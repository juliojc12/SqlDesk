# SqlLite Studio — decisões de projeto

Cliente desktop leve para consultar bancos SQL Server, MySQL e MariaDB (Windows). Host .NET 8 + WPF com WebView2 carregando um frontend React (Vite, Monaco, Tailwind).

## Estrutura

- `src/SqlDesk.Host` — WPF + WebView2, ponte de mensagens, DI
- `src/SqlDesk.Core` — conexões, execução, metadados, exportação
- `src/SqlDesk.SqlAnalysis` — ScriptDom (T-SQL) e analisador léxico do MySQL: separação de statements, travas
- `src/SqlDesk.Web` — React + Vite + Monaco
- `tests/` — testes de Core e SqlAnalysis; `tests/SqlDesk.Integration.Tests` (MySQL e MariaDB em Docker, ver `tests/docker`)

## Decisões registradas

(Decisões tomadas onde a especificação era omissa; critério: a opção mais segura para os dados.)

- **Desenvolvimento:** em Debug o WebView2 aponta para `http://localhost:5173` (`npm run dev` em `src/SqlDesk.Web`); a variável `SQLDESK_DEV_URL` sobrescreve a URL.
- **Release:** `dotnet publish src/SqlDesk.Host -c Release` roda `npm run build`, embute `dist/` como recursos e os extrai em `%LOCALAPPDATA%\SqlDesk\web\<hash>`, servidos por `SetVirtualHostNameToFolderMapping` em `https://app.sqldesk`.
- **Barra de título:** customizada (nome do app, painel lateral, configurações e botões da janela), com a área de trabalho respeitada ao maximizar.
- **Conexões (fase 2):** a senha é gravada com DPAPI (escopo do usuário) e nunca volta ao frontend; o diálogo só recebe `hasPassword`. Senha em branco ao editar mantém a salva; a connection string gerada para uma conexão já salva omite a senha.
- **Só autenticação SQL:** `Integrated Security`/`Trusted_Connection` e `Authentication` diferente de SQL Password são rejeitados ao colar a connection string. Palavras-chave que o SqlClient não conhece também são rejeitadas (mais seguro que descartá-las em silêncio).
- **Timeout de comando** não é uma palavra-chave suportada de forma portável na connection string: fica só no campo e é aplicado ao `SqlCommand`. Se vier `Command Timeout` na string colada, é lido para o campo.
- **`connections.json` corrompido:** o app mostra o erro e não sobrescreve o arquivo.
- **Conectar/desconectar e "nova query":** cada aba tem a sua sessão; duplo clique numa conexão abre uma nova query, e a conexão só é aberta para a aba ativa (sem senha salva, a senha é pedida na hora e não é gravada).
- **Aparência (fase 3):** `model-app.png` é a referência visual. O título exibido é "SqlLite Studio" (como no mockup); `SqlDesk` segue como nome interno dos projetos. Só tema escuro, por tokens CSS (`index.css`): o tema claro e o acompanhamento do sistema foram removidos na fase 9, por decisão do usuário.
- **Janela sem moldura:** a barra de título é desenhada pelo frontend (`app-region: drag`); ao maximizar, a janela respeita a área de trabalho do monitor (não cobre a barra de tarefas).
- **Sessões por aba:** uma `SqlConnection` por aba, aberta ao exibir a aba ativa (as demais conectam quando ativadas). Na restauração das abas só se reconecta sozinho quando a senha está salva; sem senha salva o app pergunta (a senha digitada fica só em memória, até fechar o app).
- **Monaco offline:** o editor é empacotado no próprio build (sem CDN), versão fixada em 0.52.2.
- **Salvar `.sql`:** UTF-8 com BOM, para abrir com acentos corretos no SSMS e no Bloco de Notas.
- **Abas e texto:** o estado das abas (incluindo texto não salvo) fica em `%APPDATA%\SqlDesk\session.json`.
- **Análise de SQL (fase 4), tudo em `SqlDesk.SqlAnalysis`, sem regex:** separação por `GO` com um lexer próprio (strings, `[ident]`, `"ident"`, comentários de linha e de bloco aninhados) e detecção dos perigos pela AST do ScriptDom (`TSql160Parser`).
- **Escolhas conservadoras nas travas:** além do que a especificação lista, bloqueia qualquer `DROP` (TRIGGER, SYNONYM, SEQUENCE, TYPE...) e `ALTER TABLE ... DROP COLUMN` (apaga dados); `DROP` de tabela temporária também bloqueia. `WHERE` que não filtra (sem coluna, `1=1`, `id = id`, `id = 5 OR 1=1`) equivale a sem `WHERE`.
- **Trecho que não parseia:** se contém `UPDATE`/`DELETE`/`TRUNCATE`/`DROP` (achados pelos tokens, não por texto), é tratado como perigoso (`Unanalyzable`), sem pré-visualização com `OUTPUT`. Sem essas palavras, só gera o erro de sintaxe.
- **SQL dinâmico:** `EXEC('...')` com literais é analisado por dentro (senão seria um atalho para burlar as travas); SQL montado em tempo de execução e `sp_executesql` só geram **aviso**, porque o conteúdo não pode ser analisado antes de executar. Procedures armazenadas que fazem UPDATE/DELETE internamente também não são vistas.
- **Statement sob o cursor:** o parse é por batch (o `GO` não é T-SQL); se o batch do cursor não parseia, usa o bloco entre linhas em branco ou `;` (este ignora strings e comentários). Erro de sintaxe em *outro* batch não atrapalha. Comentário colado acima de um statement seleciona esse statement.
- **Linhas:** toda linha devolvida é do documento; `Batch.StartLine` permite converter a linha relativa ao batch que o SQL Server reporta.
- **`GO n`:** a contagem fica em `Batch.RepeatCount`; quem executa decide o que fazer (repetir um batch de escrita exige cuidado).
- **Reescrita com `OUTPUT`:** `UPDATE` ganha `OUTPUT deleted.*, inserted.*` e `DELETE` ganha `OUTPUT deleted.*`, gerados pelo `Sql160ScriptGenerator`. **Limitação do SQL Server:** `OUTPUT` sem `INTO` falha (erro 334) em tabela com trigger habilitado; a fase 6 precisa tratar essa falha (desfazer e oferecer execução sem pré-visualização). O formato do statement reescrito muda (fica em uma linha), então linhas de erro posteriores no mesmo batch podem deslocar.
- **Execução e resultados (fase 5):** `ExecutionPlanner` (Core) decide o que rodar a partir do texto, do cursor e da seleção que o frontend envia (seleção exata > statement sob o cursor > script inteiro com F5) e passa o texto por `SqlScriptAnalyzer.Analyze` antes de qualquer comando chegar ao banco. `QueryRunner` executa os batches na conexão da aba, **um comando por vez por aba**, e **para no primeiro erro**.
- **Travas na fase 5:** como o fluxo de dupla confirmação com transação só existe na fase 6, qualquer texto com perigo (`UPDATE`/`DELETE` sem `WHERE`, `TRUNCATE`, `DROP`, trecho não analisável) é **recusado**: nada vai ao banco e as linhas bloqueadas aparecem em Mensagens. `GO n` (repetir batch) também é recusado, pela mesma razão. Erro de sintaxe apontado pelo ScriptDom sem palavra destrutiva não impede a execução: quem decide é o SQL Server.
- **Fluxo de resultados:** a ponte envia eventos `query.started`, `query.resultStarted`, `query.rows` (lotes de 500 linhas, ou antes se o lote demora mais de 200 ms), `query.resultCompleted` e `query.message`; a resposta de `query.execute` chega depois de todos. Cada execução tem um `executionId` e eventos de execuções antigas são descartados. A resposta usa o campo `message` (nunca `error`, que colide com o envelope de erro).
- **Limite de linhas:** 10 mil por result set; o resto é descartado pelo servidor ao passar para o próximo result set. O resultado fica marcado como truncado e "Carregar todas" **reexecuta o trecho que o gerou** (o texto é guardado no momento da execução, mesmo que o editor mude), sem limite, substituindo os resultados da aba.
- **Valores na grade:** `decimal` e `bigint` viajam como texto (o JS só tem `double`); datas em ISO; binário em hexadecimal (64 bytes); texto acima de 50 mil caracteres é cortado na grade (a exportação da fase 8 lê o valor completo).
- **Mensagens:** `PRINT`/avisos (`InfoMessage`), linhas afetadas por statement (`StatementCompleted`, como no SSMS), erros e tempo. A linha do erro vem relativa ao batch e é convertida para o documento; erros dentro de procedures não têm linha clicável, porque a linha é relativa à procedure.
- **Sub-abas:** Ctrl+Enter e F5 substituem os resultados e as mensagens da aba; Ctrl+\ preserva os anteriores e continua a numeração. Clicar numa sub-aba destaca no editor o **batch** que a gerou (não o statement exato: com vários statements no mesmo batch, o destaque cobre o batch inteiro).
- **Grade:** virtualizada (linhas de altura fixa, só as visíveis no DOM), ordenação no cliente com collation `pt-BR` (NULL primeiro; Shift acrescenta colunas), colunas redimensionáveis e reordenáveis, seleção por clique/Shift/arrasto, Ctrl+C em formato tabulado (NULL vira vazio; Ctrl+Shift+C ou a opção copia com cabeçalho).
- **Cancelamento:** Esc ou botão Parar cancelam via `CancellationToken` (o SqlClient envia o cancelamento ao servidor); fechar ou desconectar a aba também cancela. Esc só é consumido quando há execução em andamento.
- **Travas e transações (fase 6):** a análise da fase 4 agora alimenta a dupla confirmação. Texto com perigo (`UPDATE`/`DELETE` sem `WHERE`, `TRUNCATE`, `DROP`, trecho não analisável) volta como `needs_confirmation` e **nada é executado** (nem os statements anteriores). Só com `confirmDangerous` o backend reexecuta o mesmo texto/cursor/seleção, **reanalisando** (o frontend nunca decide o que é perigoso). `GO n` continua recusado.
- **Execução com travas (`GuardedRunner`):** abre `BEGIN TRANSACTION` (ou `SAVE TRANSACTION sqldesk_xxxx` se a aba já tem transação), conta as linhas de `TRUNCATE`/`DROP TABLE` com `COUNT_BIG(*)` dentro da transação, executa o texto reescrito com `OUTPUT` e deixa a decisão pendente (`pending_decision`). Erro, cancelamento ou falha inesperada fazem rollback sozinho. O prazo de 120 s faz rollback automático e avisa (`query.guardExpired`); uma segunda resposta tardia falha com `guard_expired`. Enquanto há decisão pendente, a aba recusa novas execuções, Commit/Rollback soltos e `BEGIN`.
- **Savepoint:** com transação já aberta na aba, Rollback desfaz só o trecho (`ROLLBACK TRANSACTION <savepoint>`) e Commit **não grava nada**: as alterações ficam na transação do usuário, que continua precisando de commit (o diálogo diz isso).
- **Erro 334 (trigger):** `OUTPUT` sem `INTO` falha em tabela com trigger. O backend desfaz, reabre a transação e executa **sem** o `OUTPUT`, ainda com a segunda confirmação, só sem a amostra do antes e depois (aviso no diálogo, com o total de linhas afetadas).
- **Correlação de amostras:** cada UPDATE/DELETE reescrito devolve um result set, ligado ao statement pela ordem. Se a quantidade de result sets não bate com a de statements reescritos (IF, loop, SELECTs no meio), a correspondência é marcada como **aproximada** e não há amostra; o diálogo avisa. A contagem de linhas vem do `StatementCompleted` (o servidor sabe o total mesmo quando o cliente cortou o `OUTPUT`); a amostra tem até 200 linhas.
- **Transação encerrada pelo script:** se o próprio texto dá `COMMIT`/`ROLLBACK` e o `@@TRANCOUNT` cai abaixo do esperado, não há mais o que desfazer: sem segunda confirmação, com aviso (`tran_lost`). `DROP DATABASE` não roda dentro de transação no SQL Server: falha, o rollback é feito e nada muda.
- **Recomendação de TRANSACTION:** `UPDATE`/`DELETE`/`MERGE` com filtro, em aba sem transação aberta, mostram a barra acima do editor (`advise_transaction`, nada executado): "Envolver em transação" insere `BEGIN TRAN;` antes e `-- COMMIT;`/`-- ROLLBACK;` depois do trecho sem executar; "Executar assim mesmo" reenvia com `skipTranAdvice`; "Não perguntar nesta aba" vale só na memória, até fechar o app. `INSERT` não dispara a barra.
- **Indicador de transação:** após cada execução o backend consulta `@@TRANCOUNT` e envia `tab.transaction`; a aba mostra o selo TRAN âmbar e a barra de status, "N abas com transação aberta" com Commit/Rollback da aba ativa. Commit solto usa `WHILE @@TRANCOUNT > 0 COMMIT` (transações aninhadas).
- **Fechar aba ou app:** aba com transação abre Commit/Rollback/Cancelar antes da pergunta de salvar; desconectar também pergunta. Fechar o app com transações abertas (botão, Alt+F4, barra de tarefas) é adiado pelo host (`MainWindow.OnClosing`, pelo último `@@TRANCOUNT` conhecido) e o frontend pede a decisão de cada aba; só então chama `window.forceClose`. Se a conexão cai com transação aberta, o app avisa que o servidor a desfez.
- **Limitação conhecida:** o app só sabe de transações abertas pelo último `@@TRANCOUNT` consultado (depois de cada execução); não há monitoramento contínuo.
- **Metadados (fase 7):** `MetadataService` (Core) mantém um cache em memória **por conexão** (não por aba), carregado em segundo plano numa **conexão própria** (`TabSessionManager.OpenSideConnectionAsync`), sem disputar a conexão de uma aba em execução. Duas fases, avisadas por `metadata.updated`: schemas e objetos (`sys.objects`: tabelas, views, procedures e funções, sem objetos do sistema) e, em seguida, colunas com o tipo formatado como no T-SQL (`nvarchar(50)`, `decimal(10,2)`). As consultas são só `SELECT` em `sys.*`. Só usa a senha salva ou a já informada nesta execução: sem ela o carregamento falha com mensagem (conecte uma aba informando a senha). O cache é carregado ao conectar uma aba e ao expandir a conexão; "Atualizar metadados" (toolbar e menu da conexão) força a recarga. Não há invalidação automática depois de DDL.
- **Árvore de objetos:** a conexão expande em schema → Tabelas/Views/Procedures/Funções (só schemas com objetos; `dbo` primeiro). Duplo clique em tabela ou view abre uma nova aba com `SELECT TOP 100 * FROM schema.Tabela alias` (sem executar); em procedure, `EXEC schema.proc`. Mostra 300 itens por grupo e "Mostrar mais".
- **Autocomplete (`suggest.ts`, `sqlContext.ts`):** análise leve no frontend, sem exigir statement completo nem parseável: comentários e strings são mascarados, o statement atual é delimitado por `;`, linha `GO` ou linha em branco, e o contexto vem dos tokens antes do cursor (subconsultas entre parênteses são puladas). Depois de `FROM`/`JOIN`/`UPDATE`/`INTO`/`USING`/`TABLE`: tabelas e views (schema só quando não é `dbo`) e schemas; depois de `alias.` ou `Tabela.`: colunas com o tipo ao lado; `schema.`: objetos do schema; em `SELECT`/`WHERE`/`ON`/`GROUP BY`/`ORDER BY`/`HAVING`/`SET`: colunas das tabelas do statement (prefixadas pelo alias ou nome da tabela quando o nome existe em mais de uma), funções e palavras-chave; `EXEC`: procedures; no resto, palavras-chave e snippets (`sel`, `selt`, `selc`, `upd`, `del`, `ins`, `tran`). Depois de `FROM tabela ` a lista deixa de sugerir tabelas (é posição de alias ou palavra-chave). O espaço só abre a lista depois de FROM/JOIN/EXEC; nos demais lugares use Ctrl+Espaço ou digite. Nomes com espaço ou palavra reservada saem entre colchetes. Dentro de comentário ou string não há sugestão.
- **Alias automático (`alias.ts`):** nome simples → primeira letra; PascalCase/camelCase → a primeira letra mais as maiúsculas (`PedidoItens` → `pi`); com `_` → a primeira letra de cada parte; conflito com alias já usado no statement → número (`c`, `c1`, `c2`); palavra reservada → número (`InscricaoNacional` → `in1`). Só em `FROM` e `JOIN` (não em `UPDATE`, `INSERT INTO`, `DELETE FROM`) e não se o usuário já digitou um alias depois do nome. A opção fica ligada por padrão, num botão da toolbar (`localStorage`); a tela de configurações chega na fase 9.
- **Limitações do autocomplete:** colunas de subconsultas e CTEs (`FROM (SELECT ...) t`, `WITH x AS`) não são conhecidas; só há nomes de uma parte para tabelas locais (sem `banco.schema.tabela`); tabelas temporárias e variáveis de tabela não aparecem; funções com valor de tabela listam colunas, mas só entram em `schema.`.
- **Exportação (fase 8):** botões CSV e XLSX na barra do resultado ativo, com o "Salvar como" nativo do Windows aberto pelo host (o frontend só recebe o caminho). Dois caminhos: **linhas carregadas** (o frontend envia as linhas já na ordem de linhas e colunas da grade, então a **ordenação e a ordem de colunas atuais** são respeitadas) e **reexecução** (resultado truncado em 10 mil linhas: o diálogo pergunta se exporta só o carregado ou se reexecuta e grava tudo). A reexecução roda o texto de origem na conexão da aba, em streaming direto para o arquivo, sem o limite da grade e sem acumular linhas em memória; vale 100 mil linhas ou mais.
- **Segurança da reexecução:** reexecutar repetiria o efeito de qualquer escrita, então só reexecuta texto que **apenas lê** (`ReadOnlyAnalyzer`, por AST: só `SELECT` sem `INTO`, `DECLARE`/`SET`/`USE`/`PRINT`); `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `EXEC`, `SELECT ... INTO`, `BEGIN TRAN`, `IF`, DDL e texto com erro de sintaxe são recusados com a explicação (exporte só o carregado). Comandos destrutivos também passam pelas travas e são recusados. A reexecução **não aplica a ordenação da grade** (só a ordem das colunas): ordenar milhões de linhas exigiria acumulá-las; o diálogo avisa quando há ordenação ativa.
- **Arquivo atômico:** a exportação grava em `arquivo.sqldesk-part` ao lado do destino e só o move para o nome final ao terminar; erro, cancelamento ou falha não deixam arquivo pela metade nem apagam um arquivo anterior de mesmo nome. A notificação mostra o progresso (a cada 5 mil linhas) com Cancelar e, ao concluir, linhas, tempo e **Abrir arquivo / Abrir pasta**, que só aceitam arquivos que o próprio app gerou (registro em memória).
- **CSV:** UTF-8 com BOM, separador `;` por padrão (seletor "CSV ;/CSV ," ao lado dos botões, guardado no navegador), fim de linha `\r\n`, datas ISO 8601 (`2026-09-30T13:45:10`, `date` só `2026-09-30`), números com ponto decimal, bit como `1`/`0`, NULL como campo vazio, binário em hexadecimal completo. Campos com o separador, aspas, quebra de linha (`\n`, `\r`) ou espaço nas pontas vão entre aspas (o CsvHelper, por padrão, só citava `\r\n`; corrigido com `ShouldQuote`, porque um `\n` solto quebraria a linha no Excel). Não há proteção contra fórmula (campo começando com `=`, `+`, `-`, `@`): o dado sai como está.
- **XLSX (MiniExcel, streaming):** as linhas passam por uma fila limitada consumida pelo MiniExcel em outra thread (memória constante; teste com 100 mil linhas). Números continuam números, datas continuam datas (`yyyy-mm-dd hh:mm:ss`, ou `yyyy-mm-dd` para `date`), bit vira booleano; `datetimeoffset`, `time`, GUID e binário viram texto. O estilo padrão do MiniExcel deixava o cabeçalho com fonte branca sobre fundo quase transparente e sem negrito, então o app usa `TableStyles.None`, congela a primeira linha e, ao terminar, ajusta só o `styles.xml` (fonte em negrito no estilo do cabeçalho; a planilha não é tocada). Limite de 1.048.575 linhas de dados (erro claro; use CSV). Nomes de coluna repetidos ou vazios ganham sufixo (`Id`, `Id_2`, `coluna3`).
- **Limitações:** a exportação das linhas carregadas leva o valor como a grade o recebeu, ou seja, texto acima de 50 mil caracteres e binário acima de 64 bytes **já vêm cortados** (marcados com `…`); só a reexecução grava o valor completo. Um texto com vários `SELECT` exporta o result set ativo (escolhido pela posição entre os que o mesmo trecho produz), e se o resultado mudar entre a execução original e a reexecução a exportação pode sair diferente do que a grade mostrava.
- **Acabamento (fase 9) — tema:** o app tem **um único tema, o escuro** (sem tema claro nem seguir o sistema; `useTheme` e o tema `sqldesk-light` do Monaco foram removidos). A grade de resultados alterna o tom das linhas com uma listra bem sutil (`--stripe`, branco a 2,8%); a linha selecionada continua em destaque por cima.
- **Configurações** (engrenagem na barra de título ou `Ctrl+,`; guardadas como um JSON no armazenamento do WebView, `sqldesk.settings`): **limite de linhas da grade** (100 a 1.000.000, padrão 10.000; o backend também ajusta o valor à faixa em `RowLimits`, então um valor adulterado não passa; "Carregar todas" e a exportação ignoram o limite), **alias automático**, **separador do CSV** e **timeout de comando para novas conexões** (0 = sem limite; cada conexão continua guardando o seu, esta é só a proposta inicial de uma conexão nova). Valores inválidos ou fora da faixa voltam ao padrão ou são ajustados, e o diálogo avisa antes de salvar. O botão "Alias" da toolbar e o seletor de separador do CSV passaram a ser só configurações (o botão de alias continua como atalho).
- **Tratamento de erros:** o frontend tem um `ErrorBoundary` (erro de renderização mostra uma tela com a explicação e "Recarregar a interface", em vez de janela em branco; as abas voltam da sessão salva e transações abertas continuam no servidor) e avisa promessas rejeitadas sem tratamento. No host, `DispatcherUnhandledException` (aviso e o app continua aberto), `AppDomain.UnhandledException` e `UnobservedTaskException` registram o erro; o dispatcher da ponte também registra falhas que nenhum handler previu e devolve "Erro inesperado: ..." em vez de uma exceção crua. O log é `%APPDATA%\SqlDesk\logs\error.log` (só tipo, mensagem, stack e um contexto curto, **nunca o texto das consultas nem senhas**; gira em `error.log.1` ao passar de 1 MB; gravar o log nunca lança).
- **Publicação:** `dotnet publish src/SqlDesk.Host -c Release -o <pasta>` gera **um único `SqlDesk.exe`** (~71 MB: self-contained, win-x64, runtime e bibliotecas nativas embutidos e comprimidos, frontend embutido e extraído em `%LOCALAPPDATA%\SqlDesk\web\<hash>` na primeira execução); um alvo pós-publicação apaga `.pdb` e `.xml` da pasta, então só o `.exe` precisa ser distribuído. Pré-requisito: o **WebView2 Runtime** (já presente no Windows 10 e 11). Verificado copiando o `.exe` sozinho para uma pasta vazia, sem o cache de extração, e dirigindo a interface. **Não foi possível testar numa máquina física sem .NET e sem o app instalado**; o teste acima prova que o executável não depende de arquivos ao lado dele, não que uma máquina totalmente limpa o execute.
- **Validação contra SQL Server real (read-only):** além dos testes automatizados, o app publicado foi dirigido pela interface contra uma instância SQL Server 2022 usando só `SELECT`: `Ctrl+Enter`, `F5` com `PRINT` e vários result sets, resultado de 25.000 linhas (truncamento em 10.000, "Carregar todas", rolagem e ordenação), `Ctrl+\`, cancelamento de um `WAITFOR` de 40 s por `Esc` (em ~0,4 s), erro do servidor com a linha clicável, metadados reais (90 objetos), autocomplete com tabelas e colunas reais, árvore com os campos das tabelas e exportação por reexecução de 300.000 linhas em CSV (16,7 MB, 6 s) e XLSX (7,6 MB, 9 s), com pico de memória de cerca de +110 MB. Os fluxos que alteram dados (dupla confirmação, commit e rollback) foram exercitados só até a primeira confirmação, sem executar nada no banco; o restante é coberto pelos testes com fakes.
- **Correções vindas dessa validação:** a árvore podia ficar presa em "Carregando colunas…" porque o aviso final dos metadados chegava antes de o carregamento ser dado como terminado (agora o estado é encerrado antes do aviso, com teste); e o encerramento do app registrava dois erros no log (descarte do container com serviço só assíncrono, e envio de mensagem ao WebView já descartado).
- **Formatar SQL:** usa a biblioteca `sql-formatter` (dialeto T-SQL, palavras-chave em maiúsculas, indentação de 4 espaços) no frontend, e não o gerador do ScriptDom, que descarta os comentários. A formatação atua na seleção ou, sem seleção, no texto todo, como uma única edição desfazível (`Ctrl+Z`). Cada batch separado por `GO` é formatado à parte e as linhas `GO` ficam no lugar. Formatar nunca pode mudar o que o script faz, então o resultado só é aceito se, comparado token a token com o original, só mudarem espaços, quebras de linha, a indentação dentro de comentários e a caixa de palavras-chave: textos entre aspas, identificadores (inclusive a caixa, por causa de bancos com collation sensível a maiúsculas), números e símbolos têm de ser idênticos. Texto que termina dentro de uma string ou de um comentário de bloco aberto, ou qualquer divergência, cancela a operação, avisa o motivo e deixa o texto como estava.
- **Cabeçalho da grade:** cada coluna tem uma setinha de ordenação sempre visível (esmaecida sem ordenação; ▲/▼ e o número da ordem quando ordenada; Shift+clique soma colunas à ordenação). Clicar no resto do título **seleciona todas as linhas da coluna** (Shift+clique estende até a coluna clicada, e o `Ctrl+C` copia na ordem em que a grade está exibindo, sem cabeçalho). Arrastar o título continua reordenando as colunas.
- **Executar não mexe no editor:** `Ctrl+Enter`, `Ctrl+\` e `F5` não destacam mais o statement executado e nunca rolam o editor nem alteram a seleção (antes o destaque rolava até o início do statement, o que tirava do fim do texto quem estava escrevendo ali). Só clicar numa sub-aba de resultado destaca por instantes o trecho que a gerou, e só nesse caso o editor rola até ele.
- **Ícone:** um cilindro de banco de dados em azul, em três camadas, com um botão verde de "executar" (play) no canto, sobre um quadrado arredondado escuro como o tema do app. O desenho mestre é `src/SqlDesk.Host/Assets/icon.svg`; dele saem o `app.ico` (10 tamanhos de 16 a 256 px, com PNG embutido) usado no executável (`ApplicationIcon`) e no ícone da janela, o `favicon.svg` do frontend, o logo da barra de título e o `docs/icon.png` do README. O `.ico` foi gerado a partir do SVG com `@resvg/resvg-js` e legível em 16 px.
- **Seleção de células da grade (como no DBeaver):** clique seleciona uma célula; **Ctrl+clique soma ou tira células soltas** (inclusive de dentro de um bloco), Shift+clique estende um bloco, Ctrl+arrastar cria outro bloco sem perder os anteriores, Ctrl+clique no título da coluna ou no número da linha soma ou tira colunas e linhas, e Ctrl+A seleciona tudo. A seleção é uma lista de retângulos mais um conjunto de células excluídas (`gridSelection.ts`), então selecionar uma coluna de 100 mil linhas custa um retângulo. O rodapé mostra quantas células estão selecionadas. `Ctrl+C` copia só as células marcadas, em ordem de exibição (ordenação e colunas reordenadas respeitadas): entram só as linhas e as colunas que têm célula marcada, e as células não marcadas no meio saem vazias para o que se cola no Excel manter o alinhamento.
- **Carregamento do resultado:** enquanto a query roda e ainda não chegou nada dela, a área de resultados mostra um indicador (giroflex na cor da conexão, tempo decorrido e como cancelar com `Esc` ou pelo link), em vez de um resultado antigo ou de "Nenhuma mensagem". Assim que as primeiras linhas chegam, o indicador some e a grade aparece; uma faixa fina e indeterminada sob as abas continua até a execução terminar. Com `Ctrl+\` (que preserva as sub-abas anteriores) só a faixa aparece, para não esconder resultados que ficaram. A animação é desligada para quem pede menos movimento no sistema.

- **MySQL e MariaDB — provedor por conexão:** cada conexão guarda o seu banco (`provider`: `sqlserver` ou `mysql`, este vale para MySQL e MariaDB); conexões salvas antes do suporte não têm o campo e valem SQL Server. O seletor "Tipo de servidor" do diálogo troca os rótulos das opções de segurança e a porta padrão (3306). Tudo que difere entre os bancos (connection string, erros, mensagens, SQL de transação e de metadados, analisador) fica atrás de `IDatabaseProvider`; o Core e o frontend não testam o tipo do banco fora dele. O driver é o MySqlConnector.
- **Analisador léxico do MySQL:** não existe parser equivalente ao ScriptDom, então `MySqlAnalyzer` tokeniza (strings, crases, comentários, `DELIMITER`, `;`) e **erra para o lado seguro**: o que não dá para classificar e contém `UPDATE`/`DELETE`/`TRUNCATE`/`DROP`/`ALTER` é tratado como perigoso. Como o servidor, só trata como espaço o espaço ASCII e os caracteres de controle (inclusive para o `-- ` virar comentário): espaços Unicode (U+00A0, U+2003, U+3000...) são caracteres de identificador, senão `--\u00A0x` esconderia um `DROP` que o servidor executa, ou `t \u00A0WHERE` (alias) pareceria um `WHERE`. **Comentários executáveis:** o servidor executa ou ignora cada `/*! */` e `/*M! */` pela própria versão, com regras de dígitos que mudam entre MySQL e MariaDB (o MySQL 8.4 lê 6 dígitos só se vier espaço depois, senão 5; o `/*M!` do MariaDB tem 6; o MariaDB trata `/*m!` como comentário comum), e qualquer mistura pode virar outro comando (`WHERE id=1 /*!50000 OR 1 */ /*!99999 =id */` roda `id=1 OR 1` no MySQL 8). Modelar versão por versão sempre deixa brecha, então a regra é uma só: um statement que grava ou muda a estrutura (começa com `INSERT`, `UPDATE`, `DELETE`, `REPLACE`, `TRUNCATE`, `DROP`, `ALTER`, `CREATE`, `RENAME`, `PREPARE` ou `EXECUTE`, direto ou depois de `WITH`, `EXPLAIN`/`ANALYZE` ou `SET STATEMENT ... FOR`, em qualquer leitura) e tem uma abertura `/*!`, `/*M!` ou `/*m!` no próprio texto (do primeiro token até o terminador dele, no texto cru, inclusive dentro de strings) ganha um perigo `Unanalyzable`: é sempre irreversível, com a confirmação forte e execução direta. Falso positivo aceito: comentários inofensivos em comandos que gravam (`INSERT /*! IGNORE */`, `DELETE ... /*!40101 LIMIT 1 */`, `CREATE TABLE ... /*!50100 PARTITION ... */`, e as views, triggers e procedures do mysqldump, `/*!50001 CREATE ... */ /*!50013 DEFINER=... */ ...`, pedem uma confirmação forte ao restaurar um dump). Os statements que estão inteiros num comentário (`/*!40101 SET NAMES utf8mb4 */;`) não têm abertura no próprio texto e ficam como antes, e o statement seguinte não conta para o anterior. Dicas de otimizador (`/*+ ... */`) são comentário comum em todas as leituras (o servidor nunca as executa como SQL). No `IsReadOnly`, um statement com duas ou mais aberturas diferentes (abertura exata mais versão) não é só leitura. Um statement que termina dentro de um comentário executável aberto nele leva o `*/` junto (antes ia sem fechar e o servidor recusava). As **leituras alternativas** do trecho (sem escape por barra, como no `NO_BACKSLASH_ESCAPES`, e com `/*!` e `/*M!` lidos como comentário comum) rodam **sempre**, mesmo quando a leitura principal já achou um perigo: as leituras precisam concordar **nos dois sentidos** sobre os perigos (tipo, posição, alvo e contagem prévia): um perigo que só a releitura vê (por exemplo `DELETE FROM /*!99999 i */ m`, em que o comentário executável troca a tabela conforme a versão do servidor), ou um perigo da leitura principal que some na releitura embora ela execute algo naquele trecho (por exemplo `DELETE FROM /*!99999 i WHERE 1=1 OR id IN (SELECT 1 FROM */ m WHERE id=1 /*!99999 ) */`, em que o servidor roda um `DELETE` filtrado em outra tabela), vira um perigo `Unanalyzable` do trecho. Essa concordância ainda cobre o que não é comando que grava com comentário próprio (por exemplo, a string que fecha em outro lugar sem `NO_BACKSLASH_ESCAPES`, ou um comentário antes do primeiro token). O perigo `Unanalyzable` faz o diálogo e a regra de irreversível incluírem o trecho. A **contagem prévia** (`SELECT COUNT(*) FROM alvo`) só é montada com nome de identificador (palavra com `[A-Za-z0-9_$]` ou caracteres não ASCII, ou nome entre crases com as crases internas dobradas); com string (`'x'`, `"x"`) ou variável como alvo não há contagem nem alvo, para o app nunca executar texto que o usuário controla. `GO` não existe no MySQL (o texto `GO` não separa nada); `DELIMITER` existe e é tratado. `PREPARE ... FROM @var`, `EXECUTE` e `CALL` não são inspecionados por dentro (como o SQL dinâmico e as procedures do SQL Server).
- **Trava sem diff `OUTPUT`:** o MySQL não tem `OUTPUT`, então a segunda confirmação mostra a **contagem prévia** das linhas afetadas (`COUNT(*)` sobre o `WHERE`, feita dentro da transação da trava), sem amostra do antes e do depois. Tabela não transacional tem regra própria (abaixo).
- **Execução irreversível (regra do script inteiro):** o MySQL confirma sozinho DDL e comandos como `COMMIT`/`START TRANSACTION`/`LOCK`. Se qualquer statement do trecho faz isso (ou é opaco: `CALL`, bloco de código, texto não analisável), **o trecho inteiro roda direto**, sem transação, e a única confirmação é a primeira, com texto mais forte ("não dá para desfazer", botão "Executar mesmo assim"): fingir um Rollback depois de um DDL seria enganar o usuário. Os `UPDATE`/`DELETE` que vierem junto também ficam sem desfazer. Não há diálogo de Commit/Rollback nesse caminho.
- **Tabela não transacional = irreversível:** `ROLLBACK` não desfaz MyISAM, Aria (segura contra queda, mas sem transação), MEMORY, CSV etc. Antes da primeira confirmação (e de novo na execução, pela mesma função `GuardedRunner.IrreversibleReasonAsync`, para as duas nunca discordarem), o app consulta `information_schema.TABLES` (consulta parametrizada, na conexão da aba) com o banco e a tabela de cada alvo dos `UPDATE`/`DELETE` perigosos. Só `InnoDB` conta como transacional; outro mecanismo, view (`ENGINE` nulo: grava nas tabelas de base), tabela não encontrada (inclusive temporária), alvo que não deu para reconhecer ou falha na consulta tornam o trecho irreversível (diálogo forte, execução direta). `UPDATE`/`DELETE` com mais de uma tabela (`UPDATE a, b`, `UPDATE a JOIN b`, `DELETE x FROM a JOIN x`, `DELETE ... USING`, `DELETE FROM a, b`) não têm um alvo só: ficam sem alvo (e sem contagem prévia), portanto irreversíveis, já que qualquer uma das tabelas pode não ser transacional. No SQL Server nada é consultado. Como rede de segurança para gravações que essa checagem não vê (trigger, outro comando sem perigo no mesmo trecho, tabela `TEMPORARY` não InnoDB com o mesmo nome de uma tabela InnoDB, que a consulta não enxerga e lê como a InnoDB), depois de cada `ROLLBACK` da trava o app lê `SHOW WARNINGS` e, com o aviso 1196, diz "Rollback feito, mas tabelas não transacionais (por exemplo MyISAM) não foram desfeitas" em vez de "as alterações foram desfeitas".
- **Marca de savepoint como defesa em tempo de execução:** nos bancos que confirmam DDL sozinhos, a trava cria um savepoint antes do script e o confere no fim; se ele sumiu, algo confirmou a transação (um commit que a análise léxica não viu, p. ex. dentro de uma procedure), não há o que desfazer e o resultado volta como `tran_lost`, sem segunda confirmação.
- **Sonda de transação aberta:** o MySQL não tem `@@TRANCOUNT`. A sonda (`MySqlTransactionProbe`) tenta `@@in_transaction` (só existe no MariaDB) e, no MySQL, `SAVEPOINT` seguido de `RELEASE SAVEPOINT`: fora de transação o `RELEASE` falha com 1305. O `performance_schema.events_transactions_current` foi descartado: um usuário comum recebe erro 1142 e, com o consumidor desligado, ele devolveria 0 em silêncio. Se a sonda não consegue responder (`null`), o app usa um contador rastreado das transações que ele mesmo abriu. O indicador, o diálogo de fechar aba e o Commit/Rollback soltos continuam valendo (`COMMIT` solto, sem aninhamento).
- **`encrypt`/`trust` → `SslMode`:** as duas opções do diálogo viram `SslMode=None` (sem criptografia), `Required` (criptografa e aceita o certificado não verificado) ou `VerifyCA` (criptografa e valida a cadeia do certificado); numa connection string colada, `Disabled` vira "sem criptografia", `VerifyFull` vira "criptografa e valida" e `Preferred` vira "criptografa e aceita o certificado". Só autenticação por usuário e senha; palavras-chave desconhecidas são rejeitadas, como no SQL Server. Também são recusadas, ao colar, ao montar e ao salvar a conexão (depois de passar pelo nome canônico do driver, para pegar apelidos como `Protocol`, `Pipe`, `Ssl-Cert` e `CA Certificate File`): `AllowLoadLocalInfile`, `CertificateFile`, `CertificatePassword` (ficaria em texto puro no `connections.json`), `CertificateThumbprint`, `CertificateStoreLocation`, `SslCert`, `SslKey`, `SslCa`/`CACertificateFile`, `ConnectionProtocol` (exceto TCP), `PipeName`, `ServerRsaPublicKeyFile` e `ServerSPN`. Em Avançado também não entram as chaves com campo próprio (senha, servidor, porta, banco, usuário, `SslMode`, timeouts), que sobrescreveriam o formulário. `AllowPublicKeyRetrieval` continua permitido (necessário para `caching_sha2_password` sem TLS).
- **Valores e tipos no MySQL:** `AllowZeroDateTime=true`, para uma data `0000-00-00` não derrubar a leitura (vira texto na grade e na exportação). `INT UNSIGNED` e `BIT` são numéricos no XLSX; `BIGINT UNSIGNED` vai como texto na grade e como número no XLSX, **perdendo dígitos acima de 2^53** (o CSV sai completo). `TINYINT(1)` vira booleano, `TIME` passa de 24 h (`838:59:59`), `BLOB` em hexadecimal.
- **Metadados sem nível de schema:** no MySQL banco e schema são a mesma coisa. A árvore tem **bancos** no primeiro nível (menos `mysql`, `information_schema`, `performance_schema` e `sys`), lidos do `information_schema`; o banco atual da conexão é o schema padrão do autocomplete (nomes sem prefixo preferem esse banco, sem diferenciar maiúsculas). Duplo clique abre `SELECT * FROM banco.tabela alias LIMIT 100` (procedure: `CALL`), com crases só onde precisar.
- **Formatador do MySQL (recusa quando não tem certeza):** usa o dialeto `mysql` do `sql-formatter` e a mesma regra de só aceitar o resultado se o conteúdo do script não mudar. Recusa **qualquer** comentário executável (`/*! */`, `/*!NNNNN */`, `/*M! */`), porque o SQL dentro dele é executado e a verificação não o enxerga, e dicas de otimizador (`/*+ */`) cujo fim real não dá para provar (o analisador as trata como comentário comum, mas o formatador continua recusando); só as palavras reservadas de todas as versões do MySQL podem mudar de caixa, e a caixa dos nomes (de tabela e de coluna) nunca muda, porque pode ser significativa conforme o servidor. No MySQL as linhas `GO` não têm tratamento especial.
- **Cancelamento no MySQL:** o servidor atende o `KILL QUERY` sem erro quando o comando é interrompível (`SELECT SLEEP(30)` devolve 1 e termina "com sucesso"), então o `QueryRunner` marca como cancelada toda execução que termina com o cancelamento já pedido. A mensagem desse caso é outra ("Cancelamento pedido, mas o servidor devolveu o resultado sem erro: o comando pode ter sido interrompido ou já ter terminado. Confira os dados (as alterações podem ter sido gravadas).") porque, sem erro do servidor, não dá para distinguir um comando interrompido pelo `KILL QUERY` de um que já tinha terminado, e o que foi gravado pode ter ficado; "Execução cancelada pelo usuário." fica só para quando o driver de fato interrompeu.
- **Testes de integração (MySQL 8 e MariaDB 11):** `tests/SqlDesk.Integration.Tests` usa o caminho real (`TabSessionManager`, `QueryRunner`, `GuardedRunner`) contra containers descartáveis (`tests/docker`, dados em tmpfs). A senha vem só de `SQLDESK_TEST_PWD`, nunca de arquivo; sem ela, ou com um container fora do ar, os testes ficam como pulados. Cada teste usa tabelas de nome único (InnoDB; MyISAM só nos testes de tabela não transacional) e as apaga no fim, e só toca no banco `sqldesk_test`.
- **Reexecução para exportar no MySQL:** aceita `SELECT` que chama funções de usuário (`SELECT f()`) e funções como `GET_LOCK` ou `NEXTVAL`. No MySQL uma função armazenada pode gravar dados, e essas funções têm efeito colateral: a reexecução roda a consulta de novo, com os mesmos efeitos.
- **Lacunas conhecidas do MySQL:** a checagem de mecanismo só olha o alvo dos `UPDATE`/`DELETE` perigosos (o resto depende do aviso 1196 no `ROLLBACK`); o autocomplete usa as palavras-chave e os snippets do T-SQL (não há lista própria do MySQL); no MariaDB os tipos inteiros vêm como `int(11)`; o analisador não olha dentro de `PREPARE`/`CALL`; a validação com a interface do WPF contra MySQL real não foi feita por automação (só os testes de integração do backend e os testes do frontend).

## Avisos de erro

- A faixa vermelha de erro some sozinha depois de 7 s (até 20 s, conforme o tamanho do texto). Só os avisos críticos ficam até o usuário fechar: hoje, a queda de conexão que desfez uma transação aberta.
- O "Canceled" que aparecia como "Erro inesperado: Canceled: Canceled" era o Monaco rejeitando a promessa de uma sugestão ou formatação cancelada. Cancelamentos (Monaco, `AbortError` e o código `cancelled` do backend) deixaram de gerar aviso; erros reais mostram "Ocorreu um erro inesperado na interface: <motivo>". A lógica está em `rejections.ts`.

## Consulta com IA

- **Primeira chamada de saída do app, opt-in:** nada sai da máquina até o usuário cadastrar uma chave em Configurações e ligar o modo IA. A chamada HTTP fica no backend (`SqlDesk.Core/Ai/AiClient`): em Release a interface roda em `https://app.sqldesk/` (CORS bloquearia) e a chave não pode ficar ao alcance do JavaScript.
- **O que sai:** o pedido digitado e o esquema compacto (`tabela(coluna tipo, ...)`, até 24 mil caracteres, priorizando o que o pedido menciona). Nunca linhas de dados. O aviso está no diálogo de configurações.
- **Chave de API:** `%APPDATA%\SqlDesk\ai.json`, protegida com DPAPI (entropia própria `SqlDesk.ai.v1`). O frontend só recebe `hasKey`; provedor e modelo ficam no mesmo arquivo. Só o liga/desliga do modo fica em `localStorage`.
- **Provedores compatíveis com a OpenAI:** NVIDIA, Groq, OpenRouter, Cerebras, Mistral e Ollama têm endereço fixo no código (`AiProviders`); "Outro" aceita um endereço informado, só `https` (ou `http` para `localhost`/loopback), sem usuário, query nem fragmento, porque a chave é enviada para ele. Cada provedor tem modelo, endereço e chave próprios: trocar de provedor nunca envia a chave de um para o endereço de outro. O `HttpClient` não segue redirecionamentos. Esses provedores não recebem `response_format` (nem todo servidor o aceita); a leitura da resposta tolera cercas de código e remove blocos `<think>`.
- **Trava independente do modelo:** `AiSqlGuard` (SqlAnalysis) exige um único comando começando com `SELECT`/`WITH`, recusa `INTO`, `EXEC`, `OPENROWSET`, `xp_`/`sp_`, `SLEEP`, `LOAD_FILE`, `FOR UPDATE`, comentários executáveis do MySQL etc. (olhando o texto cru, então há falsos positivos aceitos) e ainda consulta `ISqlAnalyzer.IsReadOnly` do provedor. O `writesData` que o modelo devolve é ignorado: quem decide é a trava.
- **Nunca executa:** o resultado só entra no editor. Reprovado na trava, entra comentado linha a linha (`-- `), de modo que um `Ctrl+Enter` acidental não rode nada; descomentar e executar passa pelas travas e confirmações de sempre.
- **Registro de erros:** nenhuma mensagem de erro de IA inclui a chave, o pedido ou o corpo da resposta do provedor.
- **Fora do escopo (v1):** chat com histórico, nova tentativa automática, chaves estrangeiras no contexto e endpoints compatíveis com OpenAI (Ollama, Azure).
